## 4. KODE SKRIP DDL LENGKAP (`po3_erd_25430116.sql`)

Berikut adalah keseluruhan skrip DDL SQL yang digunakan untuk menginisialisasi basis data `kopma` beserta struktur tabel dan batasan referensialnya:

```sql
-- Pembuatan Basis Data
CREATE DATABASE kopma;
USE kopma;

-- 1. Tabel Petugas
CREATE TABLE petugas (
    id_petugas INT(11) PRIMARY KEY AUTO_INCREMENT,
    nama_petugas VARCHAR(50),
    username VARCHAR(30),
    password VARCHAR(35),
    peran_petugas ENUM('admin','kasir')
);

-- 2. Tabel Anggota
CREATE TABLE anggota (
    id_anggota VARCHAR(10) PRIMARY KEY,
    nama_anggota VARCHAR(100),
    jk_anggota CHAR(1),
    tempat_lahir_anggota VARCHAR(50),
    tgl_lahir_anggota DATE,
    prodi_anggota VARCHAR(100),
    no_hp_anggota VARCHAR(15),
    status_anggota VARCHAR(20),
    tgl_daftar_anggota DATE
);

-- 3. Tabel Pemasok
CREATE TABLE pemasok (
    id_pemasok INT(11) PRIMARY KEY AUTO_INCREMENT,
    nama_pemasok VARCHAR(100),
    telp_pemasok VARCHAR(15),
    alamat_pemasok VARCHAR(200)
);

-- 4. Tabel Barang
CREATE TABLE barang (
    kd_barang VARCHAR(10) PRIMARY KEY,
    nama_barang VARCHAR(100),
    kategori_barang VARCHAR(50),
    harga_jual_barang DECIMAL(10,2),
    stok_barang INT(11),
    stok_min_barang INT(11)
);

-- 5. Tabel Penjualan (Header Transaksi Penjualan)
CREATE TABLE penjualan (
    no_penjualan VARCHAR(12) PRIMARY KEY,
    no_nota_penjualan VARCHAR(20),
    tgl_penjualan DATETIME,
    jml_penjualan SMALLINT(6),
    total_penjualan DECIMAL(10,2),
    id_petugas INT(11),
    id_anggota VARCHAR(10),
    bayar_penjualan DECIMAL(10,2),
    FOREIGN KEY (id_petugas) REFERENCES petugas(id_petugas),
    FOREIGN KEY (id_anggota) REFERENCES anggota(id_anggota)
);

-- 6. Tabel Detail Penjualan (Item Transaksi Penjualan)
CREATE TABLE detail_penjualan (
    no_penjualan VARCHAR(12),
    kd_barang VARCHAR(10),
    qty_detail_penjualan INT(11),
    harga_satuan_detail_penjualan DECIMAL(10,2),
    PRIMARY KEY (no_penjualan, kd_barang),
    FOREIGN KEY (no_penjualan) REFERENCES penjualan(no_penjualan),
    FOREIGN KEY (kd_barang) REFERENCES barang(kd_barang)
);

-- 7. Tabel Pembelian (Header Transaksi Pembelian/Pengadaan)
CREATE TABLE pembelian (
    id_pembelian INT(11) PRIMARY KEY AUTO_INCREMENT,
    no_faktur_pembelian VARCHAR(20),
    tgl_pembelian DATE,
    jml_pembelian INT(11),
    id_pemasok INT(11),
    status_pembelian VARCHAR(30),
    FOREIGN KEY (id_pemasok) REFERENCES pemasok(id_pemasok)
);

-- 8. Tabel Detail Pembelian (Item Transaksi Pembelian)
CREATE TABLE detail_pembelian (
    id_pembelian INT(11),
    kd_barang VARCHAR(10),
    qty_detail_pembelian INT(11),
    harga_beli_detail_pembelian DECIMAL(10,2),
    PRIMARY KEY (id_pembelian, kd_barang),
    FOREIGN KEY (id_pembelian) REFERENCES pembelian(id_pembelian),
    FOREIGN KEY (kd_barang) REFERENCES barang(kd_barang)
);
```

## 5. ANALISIS WAJIB

Analisis mendalam mengenai arsitektur basis data, struktur entitas, kardinalitas, integritas data, normalisasi, dan alur proses bisnis koperasi diuraikan sebagai berikut:

### 5.1. Analisis Entitas, Atribut, dan Kamus Data (Data Dictionary)

Sistem Basis Data Koperasi Mahasiswa ini terdiri dari **8 entitas** yang dikelompokkan ke dalam dua kategori fungsional: **Entitas Master (Master Data)** dan **Entitas Transaksi (Transactional Data)**.

#### A. Kelompok Entitas Master
1. **Entitas `petugas`**
   - **Fungsi**: Menyimpan data akun pengelola/petugas KOPMA yang berhak melakukan transaksi kasir dan manajemen sistem.
   - **Atribut Kunci**: `id_petugas` (Primary Key, integer berurutan otomatis `AUTO_INCREMENT`).
   - **Atribut Lain**: `nama_petugas` (identitas nama), `username` dan `password` (kredensial autentikasi), serta `peran_petugas` (tipe `ENUM('admin','kasir')` untuk pembatasan hak akses / RBAC).

2. **Entitas `anggota`**
   - **Fungsi**: Menyimpan informasi mahasiswa/civitas akademika yang terdaftar sebagai anggota koperasi.
   - **Atribut Kunci**: `id_anggota` (Primary Key, varchar kode unik seperti Nomor Anggota/NIM).
   - **Atribut Lain**: `nama_anggota`, `jk_anggota` (CHAR 1 digit 'L'/'P'), `tempat_lahir_anggota`, `tgl_lahir_anggota` (DATE), `prodi_anggota`, `no_hp_anggota`, `status_anggota` (aktif/nonaktif), dan `tgl_daftar_anggota`.

3. **Entitas `pemasok`**
   - **Fungsi**: Menyimpan data rekanan/supplier penyuplai stok komoditas ke KOPMA.
   - **Atribut Kunci**: `id_pemasok` (Primary Key, integer `AUTO_INCREMENT`).
   - **Atribut Lain**: `nama_pemasok`, `telp_pemasok`, dan `alamat_pemasok`.

4. **Entitas `barang`**
   - **Fungsi**: Katalog barang inventaris yang diperjualbelikan oleh koperasi.
   - **Atribut Kunci**: `kd_barang` (Primary Key, varchar kode unik barcode/SKU produk).
   - **Atribut Lain**: `nama_barang`, `kategori_barang`, `harga_jual_barang` (DECIMAL(10,2) menjamin ketelitian moneter), `stok_barang` (jumlah fisik terkini), serta `stok_min_barang` (batas ambang peringatan *reorder point* persediaan).

#### B. Kelompok Entitas Transaksi
5. **Entitas `penjualan` (Header Penjualan)**
   - **Fungsi**: Menyimpan data faktur induk transaksi penjualan barang kepada anggota/pelanggan.
   - **Atribut Kunci**: `no_penjualan` (Primary Key, kode unik transaksi).
   - **Foreign Keys**: `id_petugas` (merujuk ke petugas kasir), `id_anggota` (merujuk ke pembeli terdaftar).
   - **Atribut Finansial**: `tgl_penjualan` (DATETIME mencatat waktu transaksi), `jml_penjualan` (total ragam item), `total_penjualan` (akumulasi rupiah), dan `bayar_penjualan` (nominal pembayaran tunai/transfer).

6. **Entitas `detail_penjualan` (Junction Table)**
   - **Fungsi**: Menyimpan rincian item barang spesifik dalam setiap nota penjualan.
   - **Atribut Kunci**: `PRIMARY KEY (no_penjualan, kd_barang)` (Composite Primary Key).
   - **Atribut Transaksi**: `qty_detail_penjualan` (kuantitas unit), `harga_satuan_detail_penjualan` (perekaman harga riil saat transaksi berlangsung, mencegah inkonsistensi jika harga master di kemudian hari berubah).

7. **Entitas `pembelian` (Header Pembelian / Restok)**
   - **Fungsi**: Menyimpan data faktur induk pembelian stok barang dari pihak pemasok.
   - **Atribut Kunci**: `id_pembelian` (Primary Key, integer `AUTO_INCREMENT`).
   - **Foreign Key**: `id_pemasok` (merujuk ke supplier pemasok barang).
   - **Atribut Tambahan**: `no_faktur_pembelian`, `tgl_pembelian`, `jml_pembelian`, dan `status_pembelian` (misal: 'Lunas', 'Menunggu', 'Diterima').

8. **Entitas `detail_pembelian` (Junction Table)**
   - **Fungsi**: Menyimpan rincian setiap macam barang yang dipasok dalam suatu faktur pembelian.
   - **Atribut Kunci**: `PRIMARY KEY (id_pembelian, kd_barang)` (Composite Primary Key).
   - **Atribut Transaksi**: `qty_detail_pembelian` (jumlah unit masuk), `harga_beli_detail_pembelian` (harga pokok pembelian per unit).

### 5.3. Analisis Dekomposisi Relasi Many-to-Many (M:N) dan Kunci Komposit (Composite Primary Key)

Dalam operasional koperasi sehari-hari:
- **Kasus Penjualan**: Satu transaksi penjualan dapat memuat banyak jenis barang, dan satu jenis barang dapat dibeli di banyak transaksi penjualan yang berlainan (*relasi M:N* antara `penjualan` dan `barang`).
- **Kasus Pembelian**: Satu faktur pengadaan dapat mencakup banyak produk dari supplier, dan satu produk dapat dipasok berulang kali melalui faktur yang berbeda (*relasi M:N* antara `pembelian` dan `barang`).

Dalam basis data relasional (RDBMS), relasi *Many-to-Many* tidak dapat diimplementasikan langsung ke dalam dua tabel tanpa memicu redundansi berlebih atau melanggar *First Normal Form* (multivalued attribute). Oleh karena itu:
1. **Penyelesaian dengan Tabel Perantara (*Associative/Junction Table*)**:
   - Membentuk tabel `detail_penjualan` untuk memecah relasi M:N menjadi dua relasi One-to-Many:
     $$\text{penjualan } (1) \longrightarrow (N) \text{ detail\_penjualan } (N) \longleftarrow (1) \text{ barang}$$
   - Membentuk tabel `detail_pembelian` untuk memecah relasi M:N menjadi dua relasi One-to-Many:
     $$\text{pembelian } (1) \longrightarrow (N) \text{ detail\_pembelian } (N) \longleftarrow (1) \text{ barang}$$
2. **Penerapan Composite Primary Key**:
   - Pada tabel `detail_penjualan`:
     ```sql
     PRIMARY KEY (no_penjualan, kd_barang)
     ```
     Kombinasi antara `no_penjualan` dan `kd_barang` memastikan bahwa satu barang yang sama tidak boleh diduplikasi barisnya dalam satu nota transaksi yang sama. Jika pembeli menambah jumlah, atribut `qty_detail_penjualan` yang diperbarui.
   - Pada tabel `detail_pembelian`:
     ```sql
     PRIMARY KEY (id_pembelian, kd_barang)
     ```
     Menjamin keunikan baris barang dalam satu surat faktur pengadaan.

### 5.4. Analisis Integritas Data (Data Integrity Constraints)

Skema basis data ini menerapkan tiga pilar integritas data:
1. **Entity Integrity (Integritas Entitas)**:
   - Setiap tabel memiliki Primary Key yang unik dan tidak bernilai `NULL`.
   - Penggunaan `AUTO_INCREMENT` pada `id_petugas`, `id_pemasok`, dan `id_pembelian` menjamin nilai kunci pengganti (*surrogate key*) selalu naik secara unik tanpa tabrakan data.
2. **Referential Integrity (Integritas Referensial)**:
   - Ditegakkan menggunakan klausul `FOREIGN KEY (...) REFERENCES ...`.
   - Mengikat record anak (*child table*) ke tabel induk (*parent table*). Sebagai contoh, sistem menolak memasukkan transaksi `penjualan` jika `id_petugas` atau `id_anggota` yang dimasukkan belum terdaftar pada tabel masternya.
3. **Domain Integrity (Integritas Domain/Nilai)**:
   - Pemilihan tipe data yang presisi:
     - `DECIMAL(10,2)` untuk nilai moneter (`harga_jual_barang`, `total_penjualan`, `bayar_penjualan`, `harga_satuan_detail_penjualan`, `harga_beli_detail_pembelian`) guna menghindari masalah pembulatan biner (*floating point precision error*).
     - `ENUM('admin', 'kasir')` pada `peran_petugas` membatasi domain nilai hanya pada dua status peran yang sah.
     - `CHAR(1)` pada `jk_anggota` untuk efisiensi penyimpanan kode jenis kelamin ('L' / 'P').
     - `DATETIME` pada `tgl_penjualan` untuk merekam tanggal dan jam hingga detik secara presisi, sedangkan `DATE` pada `tgl_pembelian`, `tgl_lahir_anggota`, dan `tgl_daftar_anggota` yang hanya membutuhkan presisi harian.

---

### 5.5. Analisis Tingkat Normalisasi Basis Data (1NF, 2NF, 3NF)

Skema basis data `kopma` telah memenuhi standar normalisasi hingga **Third Normal Form (3NF)**:

1. **Bentuk Normal Pertama (1NF)**:
   - **Kriteria**: Setiap kolom hanya bernilai atomik (tunggal, bukan himpunan nilai/array), tidak ada perulangan grup atribut (*repeating groups*), dan memiliki Primary Key.
   - **Evaluasi**: Terpenuhi. Contohnya, daftar belanjaan tidak disimpan sebagai teks bergulir dalam satu kolom di tabel `penjualan`, melainkan diurai per item ke dalam tabel `detail_penjualan`.
2. **Bentuk Normal Kedua (2NF)**:
   - **Kriteria**: Memenuhi 1NF dan tidak ada ketergantungan fungsional parsial (*partial functional dependency*), di mana semua atribut non-kunci harus bergantung sepenuhnya pada *seluruh* Primary Key (khususnya tabel berkunci komposit).
   - **Evaluasi**: Terpenuhi. Pada `detail_penjualan`, atribut `qty_detail_penjualan` dan `harga_satuan_detail_penjualan` bergantung penuh pada gabungan `(no_penjualan, kd_barang)`, bukan hanya pada salah satunya.
3. **Bentuk Normal Ketiga (3NF)**:
   - **Kriteria**: Memenuhi 2NF dan tidak memiliki ketergantungan transitif (*transitive dependency*), di mana atribut non-kunci tidak boleh bergantung pada atribut non-kunci lainnya.
   - **Evaluasi**: Terpenuhi. Atribut data master pemasok tidak disimpan di tabel `pembelian`, melainkan dipisahkan ke tabel `pemasok`. Begitu pula nama dan prodi anggota dipisahkan ke tabel `anggota`, bukan disalin berulang di tabel `penjualan`.

### 6.2. Rekomendasi Pengembangan Lanjutan
1. **Penerapan Referential Actions**:
   - Untuk meningkatkan kendali relasi, dapat ditambahkan aturan aksi referensial eksplisit seperti `ON UPDATE CASCADE ON DELETE RESTRICT` pada setiap deklarasi foreign key untuk mencegah penghapusan data master yang sudah memiliki riwayat transaksi.
2. **Otomatisasi Stok dengan Trigger**:
   - Pada pengembangan modul selanjutnya, disarankan menambahkan trigger MySQL `AFTER INSERT ON detail_penjualan` untuk mengurangi `stok_barang` secara otomatis, dan `AFTER INSERT ON detail_pembelian` untuk menambah `stok_barang`.
3. **Penyimpanan Password Terenkripsi**:
   - Panjang kolom `password VARCHAR(35)` pada tabel `petugas` dapat ditingkatkan menjadi `VARCHAR(255)` guna mengakomodasi hashing modern seperti bcrypt/Argon2.
